# 反模式清单

> **本文档是 AI 在每次分析前必读的"禁忌清单"**。每条都是某次真实 AI 分析中实际发生过的失败。

## 反模式 1：用浏览器过反爬挑战取 cookie 作为最终方案

**实战案例**：瑞数 nmpa

**AI 的操作**：用 Playwright 过 RS 412 挑战拿 cookie，最终方案每 30 分钟运行一次

**AI 的辩护**："瑞数 JSVMP 保护极其复杂，纯 Node.js 几乎不可能绕过"

**为什么不成立**：
- 工作区可能已有 sdenv 纯 Node.js 方案
- AI 没看 sdenv 文档就断言"不可能"
- 最终交付在无浏览器的 Docker 容器里无法运行

**判定测试**：最终代码在无 X11、无浏览器、只有 Node.js 的 Docker 容器里，能不能稳定跑满 24 小时？

## 反模式 2：Cookie 硬编码到 headers.json

**实战案例**：抖音 /aweme/detail

**AI 的操作**：把 `ttwid` / `__ac_signature` 硬编码到 headers.json

**AI 的辩护**："cookie 有几小时有效期，不是每次请求前都要开浏览器"

**为什么不成立**：
- "几小时"还是"几天"不影响定性——cookie 过期后没有浏览器就完全无法工作
- `__ac_signature` 可以协议还原（基于 `__ac_nonce` 的签名算法）
- `ttwid` 直接请求首页就能 Set-Cookie 拿到

**判定测试**：启动代码在无浏览器环境一周，不人工干预，是否能稳定获取数据？

## 反模式 3：激活 skill 后直接 launch_browser（跳过状态准入检查）

**AI 的操作**：
```
轮 1: 激活 skill (读 SKILL.md)
轮 2: launch_browser(headless=false)
轮 3: navigate(target_url)
```

**AI 的辩护**："用户要求明确，快速开干"

**为什么不成立**：
- 工具没检测 → 工具不可用时报错浪费时间
- 经验库没查 → 重复踩坑 / 从零写已有方案
- "快速开干"其实慢得多——12 轮对话写错误方案，先完成状态准入检查

**判定测试**：翻 skill 激活后的前 3 条对话记录。前 3 条里已记录 `INTENT_CONFIRM`、`ENV_READY`、`EVIDENCE_GATE` 的进入依据 → 合规；前 3 条是 "launch_browser / navigate" → 违规

## 反模式 4：在工作区已有方案时从零建新项目

**AI 的操作**：工作区已有 `site_xxx/` 含验证方案，AI 建了 `site_xxx_new/` 从零写

**AI 的辩护**："用户要求重新使用 skill，我以为要从零开始"

**为什么不成立**：
- "重新使用 skill" ≠ "从零写代码"，而是"遵循 skill 流程"
- 遇到歧义先自动判定（按证据校验能否复用），无法判定才问用户，不是默认从零

**正确做法**：发现已有方案目录时默认复用：先校验已有方案的资源版本、参数链与本次一致（时效校验），通过 → 宣布复用后继续；不通过 → 降级为方法论参考并宣布重新分析。只有无法自动判定取舍时才问用户一次。

## 反模式 5：面对复杂 SDK 直接判定"不可能还原"

**AI 的思维过程**："如果环境补丁迭代仍无法激活 SDK 拦截器，我可能会被迫放弃纯协议路径"

**为什么这滑坡不能发生**：
- "环境补丁没让 SDK 激活"是**本步骤**的问题，不是"整个协议方案不可行"的证据
- 应该按 `IMPLEMENT` 实现梯度推进的**下一级**，而不是横向跳到浏览器
- 梯度 3-4 都没试就放弃，违反第五条原则

**正确做法**：按 `IMPLEMENT` 实现梯度逐级尝试，浏览器仅用于前置取证，不得进入最终交付路径

## 反模式 6：经验法则背诵但不执行

**AI 的表现**：复盘时能流利背出"经验法则 #1：反爬类型识别是 IDENTIFY 的前置识别"，但实际操作时完全忽略

**为什么这发生**：
- 规则写在 skill 里 ≠ 规则会被执行
- 非硬 gate 的规则（无检查机制）100% 会被忽略

**正确做法**：不靠 AI 自觉，靠硬 gate：
- 状态准入检查 必须复述输出（可被用户验证）
- 第 3 节纯协议红线违反即失败（明确后果）
- 高频站点速查表（不靠"主动想起来"而是"看到域名就命中"）

## 反模式 7：假设 signer 可无状态并发调用

**实战案例**：抖音 a_bogus 批量生成

**AI 的操作**：把 signer 写成无状态函数，多进程/多线程并发调用同一个 jsdom 实例

**AI 的辩护**："signer 是纯函数，输入相同输出相同，应该可以并发"

**为什么不成立**：
- signer 通常持有 vm context / WASM 实例 / jsdom window / Cookie 状态，不是无状态的
- bdms.init() 异步回调可能引用 undefined 导致 crash（已记录在 memory 中）
- 多线程同时操作同一个 vm context 会导致状态错乱（Cookie 串、签名输入污染）
- jsdom 不是线程安全的

**正确做法**：
- signer 单例常驻 + `process.on('uncaughtException')` 兜底（抖音项目已验证）
- 高并发场景用 signer 池（多个独立 vm context 实例）
- 跨进程调用时每个进程独立加载 signer
- WASM 实例可复用但要加锁或池化

**判定测试**：连续 100 次并发调用 signer，签名值是否稳定？签名输入是否串扰？

## 反模式 8：vm 沙箱执行成功但无输出，忽视 try-catch 静默吞错

**实战案例**：同花顺问财 iwencai hexin-v

**AI 的操作**：vm.runInContext 执行 chameleon.js，用 try-catch 包裹捕获错误，运行返回"成功"但 cookie "v" 未生成

**AI 的辩护**："vm.runInContext 没抛错说明运行成功，可能是算法逻辑没走到生成 cookie 的分支"

**为什么不成立**：
- 目标 JS **自身**在末尾 IIFE 中用 `try{init()}catch(e){return e}` 包裹初始化函数，所有初始化错误被静默吞掉
- vm.runInContext 的 try-catch 只能捕获 JS 顶层抛出的错误，**目标 JS 内部的 try-catch 吞掉的错误不会传播到外层**
- 表面"运行成功"实际是"错误被目标 JS 自己吞了"，不是真的没报错
- 这是混淆 JS 常见的反调试手段，不是算法逻辑问题

**正确做法**：
1. **识别静默吞错模式**：Grep 目标 JS 中的 `try{...}catch(...){return ...}` 模式，特别是末尾 IIFE 中的初始化包裹
2. **try-catch 透明化**：字符串替换把目标 JS 内部的 `try{fn()}catch(e){return e}` 改为 `fn()`，让真实错误抛出到 vm.runInContext 的外层 try-catch
3. **定位真实错误**：透明化后通常会暴露 `ReferenceError: XXX is not defined`（如 Element 缺失）或 `TypeError: xxx is not a function`
4. **修复后恢复原样**：补齐缺失环境后，可保留透明化版本（外层 try-catch 已能捕获）或恢复原样

**诊断信号**：
- vm.runInContext 运行成功但目标输出（cookie/全局变量/返回值）未生成
- 目标 JS 末尾有 IIFE 包裹的初始化调用
- 目标 JS 内部有 `try{...}catch(...){return ...}` 或 `try{...}catch(...){}` 模式

**判定测试**：vm.runInContext 运行后目标输出是否生成？未生成 → 检查目标 JS 是否有内部 try-catch 吞错，透明化后重新运行看真实错误。

## 反模式 9：标准哈希算法常量被篡改仍坚持纯算法还原

**实战案例**：猿人学第5题（match5）

**AI 的操作**：识别到混淆 JS 内嵌 MD5 哈希函数，用 Node.js crypto MD5(m) 计算标准哈希值作为 cookie，请求返回 `{"error":"token failed"}`，反复尝试 MD5(m)/MD5(f)/MD5(m+f)/MD5(MD5(m)) 等组合均失败

**AI 的辩护**："4 个轮函数 F/G/H/I 与标准 MD5 完全一致，应该是标准 MD5，可能是输入参数组合不对"

**为什么不成立**：
- 轮函数标准 ≠ 哈希算法标准，**T 常量表**也是 MD5 的核心组成部分
- T[22] = `Date.valueOf() - Date.parse()`（动态时间差），T[26] = `Date.valueOf()`（动态时间戳），这些是运行时动态值
- 含动态时间戳的哈希**数学上无法纯算法还原**，不是输入组合问题
- 反复尝试不同输入组合是浪费时间，应该先对比 T 常量表

**正确做法**：
1. **提取完整哈希实现**：不只是看轮函数，必须对比 T 常量表、IV（初始向量）、padding 方式
2. **识别动态常量信号**：T 常量被替换为 `Date.valueOf()`/`Date.parse()`/随机数/服务端下发值时，警惕纯算不可行
3. **动态值 ≠ 不可复现（后补修正）**：判定降级前先用时间冻结对照法验证（浏览器 init_script 冻结 Date 后输出仍可复现 ⇒ 动态常量不影响确定性）——match5 后续突破证明当年"T[22]/T[26] 动态时间戳无法纯算"的结论不准确，真正的阻断点是补环境缺 `XMLHttpRequest.DONE` 导致 MD5 分组步长退化，属 vm 沙箱补环境可修范畴，无需降级浏览器
4. **进入环境伪装或 vm 路径**：确认无法纯算后走 vm 沙箱跑原始 JS；动态常量必须保留其真实来源并在 Node.js / Python 交付入口中复现，无法证明来源时阻塞交付

**诊断信号**：
- 标准哈希算法（MD5/SHA1/SHA256）的轮函数与标准一致，但输出不匹配
- 哈希实现中有 T 常量被替换为变量（非硬编码数字）
- 变量绑定到 `Date`/`Math.random()`/`window` 等动态源

**判定测试**：提取哈希算法的 T 常量表，逐项对比标准值。有任何一项是动态值（时间戳/随机数/服务端下发）→ 纯算不可行，立即切换到 `IMPLEMENT` 的下一条纯协议实现路径。

## 反模式 10：响应体 code 非 0 + data 乱码 → 误判为风控/错误码

**实战案例**：雷速 leisu `api-gateway.leisu.com` team_info

**AI 的操作**：请求通过 WAF 挑战后拿到 `HTTP 200 + code 107 + data 二进制乱码`，先入为主认定"code 是错误码 / data 是 AES 密文"，横向排查 TLS 指纹（curl_cffi）、ssxmod cookie、acw_tc、IP 风控、acw 挑战值长度差异（55 vs 50 字符），几十步后得出"IP 风控拒绝"的错误结论，降级 sign-only 交付。

**AI 的辩护**："data 解码后 mod16=14 不是 AES 块对齐，说明是错误信息；浏览器同 IP 也失败，说明是风控。"

**为什么不成立**：
- 响应拦截器里 `if(code>=1 && code<=130) return u.a(data, code-100)` —— **`code` 是加密容器标识，`code-100` 是凯撒位移量**，根本不是错误码
- data = 凯撒位移（仅字母）+ gzip + base64 三重编码，`mod16≠0` 恰恰说明"不是 AES"，而不是"是错误信息"
- 浏览器同 IP 失败，是因为 code 语义没搞懂，不是风控

**正确做法**：
1. 响应 body 非明文 JSON 时，**先搜前端响应拦截器的 `if(code...)` 分支**，确认 code 是错误码还是加密参数（位移量/模式标识）
2. **先判 data 编码特征**（base64 解码看 magic number：`1f8b` gzip / `789c` zlib；`mod16≠0` 排除 AES），再套算法
3. 响应解密也先查 trace 的 xhrNative 响应记录（第一手证据），别先搜源码密钥串——密钥可能用于别的字段

**判定测试**：看到 `code 非 0 + data 乱码` 时，是否先搜了前端 `if(code...)` 分支 + 判了 data 编码特征？若直接跳去查 TLS / 风控 / 参数长度，即违反本条。

## 反模式 11：用过期签名做对照实验 → 误判「连接层风控不可绕过」

**实战案例**：拼多多 anti_content（apiv2 40002）

**AI 的操作**：自己的签名 + curl_cffi / tls_client 全部 403 后，把**取证阶段抓的浏览器签名**（内嵌 serverTime，已过期数分钟）经 curl_cffi 重放，同样 403，据此宣布「40002 是连接层 TLS/h2 指纹拦截，与签名内容无关，纯协议无法绕过」，随后用取证浏览器封装取数脚本当作「解决方案」交付（为过检查器还把脚本挪进 `case/`）。

**AI 的辩护**："连浏览器真实生成的签名都过不去，说明拦截在连接层，签名还原已经 100% 正确。"

**为什么不成立**：
- 内嵌 serverTime 的签名有有效期；过期签名与垃圾签名返回**同一个风控码**，对照变量根本没控住——重放 403 只能证明"过期签名被拒"，不能证明"连接被拒"
- 用新鲜浏览器签名（采集后立即重放）+ curl_cffi = HTTP 200，连接层毫无问题
- 真正根因是签名内嵌的环境检测 flag 与浏览器不一致，修复 4 个检测位后**纯 Node H1 都能 200**
- 把取证浏览器包装成取数方案违反纯协议红线，脚本挪到 `case/` 不改变其交付性质

**正确做法**：
1. 403 无法区分拦截层时，先跑分层定位矩阵的正反对照（`references/network/ip-risk-control.md`）：① 浏览器**新鲜**签名 + 纯协议客户端；② 自己的签名 + 真实浏览器连接（preload hook 注入，带执行标记验证）
2. 对照样本采集后立即重放并记录延迟；过期样本的实验结果一律作废
3. 两个对照都没做，禁止下「连接层风控」结论，禁止转投浏览器内核方案

**判定测试**：翻验证记录——宣布连接层拦截前，是否存在「新鲜浏览器签名 + 纯协议客户端」的 200/403 对照记录与「自己签名 + 浏览器连接」的反向对照记录？没有即违反本条。

## 反模式 12：未测量 SDK 内嵌的检测项就断言「需要完整复现浏览器环境」

**实战案例**：拼多多 anti_content（fbeZ SDK）

**AI 的操作**：反向对照确认「服务端校验签名内容」后，先入为主假设服务端校验 canvas 指纹、鼠标轨迹等完整浏览器数据，判定「Node 沙箱几乎不可能复现，纯协议在可接受时间内不可行」，转向手写 msgpack/gzip/自定义 base64 解码器逐字段 diff（多轮失败），几乎放弃纯协议。

**AI 的辩护**："fbeZ 采集 canvas/行为/环境多维数据，服务端能区分浏览器生成与沙箱生成，完整复现成本极高。"

**为什么不成立**：
- 「服务端校验签名内容」≠「校验全部内容」。实际被校验的只是 SDK 的 19 位环境检测输出，其中仅 4 位与浏览器不同，全部可修（Buffer 泄露、plugins、webdriver 原型、native toString）
- 结论应该来自**测量**（SDK 检测函数在浏览器与沙箱的实际输出 diff），不是来自对采集面大小的想象
- 手写解码黑盒密文是另一条歧路：对齐检测输出不需要解码签名

**正确做法**：
1. 用对齐探针法（`references/env/env-detect-bypass.md`）：注入导出 SDK 检测函数（如 `window.__fbezWt=Wt`），浏览器空白页与 Node 沙箱各采样一次，逐位 diff 得到有限差异清单
2. 混淆键语义用运行中的 SDK 解码函数批量解出（浏览器内 `W("0x..","salt")`），不静态正则抠字符串数组
3. 差异位归零后重新生成签名真实验证；对齐目标以浏览器实测输出为准（含 null 位）

**判定测试**：宣称「环境指纹无法对齐 / 需完整浏览器环境」前，是否已列出 SDK 检测函数在浏览器与沙箱的输出 diff？没有 diff 清单即违反本条。

## 反模式 13：惩罚期内继续跑诊断实验 → 全部数据无效

**实战案例**：猿人学第6题（match6）

**AI 的操作**：REAL_VERIFY 被风控拒绝后，连续做了 20+ 个诊断实验（实验 A 到 Q 系列），每个实验失败就换假设继续测。后来发现该站有失败惩罚机制——连续失败约 5-10 次后 session 进入惩罚态（连浏览器页面自身请求都被拒）。此前一半以上的实验都在惩罚期内跑的，得出的"TLS 硬门槛"结论完全是惩罚态+变量缺失的复合假象，据此还交付了浏览器自动化方案（被用户打回）。

**AI 的辩护**："实验失败了就换变量重试，多试总能定位问题。"

**为什么不成立**：
- 惩罚期内**任何请求都失败**，与变量无关——此时做的每个实验都不构成证据，只会加深惩罚
- 惩罚态的典型信号是"连原本确定成功的基线请求也失败了"（如页面自身 req(1) 渲染不出数据）——但客户端状态（如 window.i 累加）照常更新，容易误判为"请求成功"
- 基于"全部失败"数据归纳出的风控模型（状态机 v1→v10 迭代）方向全错，浪费几十轮
- **频率墙误判是同根因的另一面**：match6 早期"页间隔 ≥2 秒稳定通过"的假结论——签名未修复时失败累积进惩罚态，加 sleep 恰好给了冷却时间，被误判为"频率限制生效"；签名修复后无缝连发（65ms/页）全部通过

**正确做法**：
1. **诊断实验前先验基线**：跑一个确定应成功的请求（如重新加载页面看数据渲染），失败 ⇒ 已在惩罚期，先冷却（本例约 10 分钟+），不做任何实验
2. **设置失败预算**：连续 3-5 次诊断实验失败即停，冷却后验基线再继续；把"失败次数"本身当作待控变量记录
3. **区分"客户端成功假象"**：window 变量累加、DOM 状态变化不代表请求成功，判定成败必须看**响应体**（数据字段 vs 风控文案）
4. **怀疑频率墙先证伪**：对照浏览器语义（翻页即点即发、无人工延迟可直接证伪）；"放慢速度"类文案在确认签名正确前不得按字面归因频率

**判定测试**：诊断实验记录里，每次实验是否都附带了"基线请求当时是否成功"的佐证？连续失败 3 次以上仍无冷却记录即违反本条。

## 反模式 14：对照实验一次改多个变量 / 实验代码自身有 bug → 结论反复震荡

**实战案例**：猿人学第6题（match6）

**AI 的操作**：S11 实验"纯协议可行性测试"一次性改变了 4 个变量（开窗来源浏览器→curl_cffi、m 生成浏览器→Python、q 链初始化有→空、cookie 完整→仅 sessionid），失败后无法定位是哪个变量导致。更早的 K2v2 链扩展实验里实验代码自身有 bug（m 内 t 与 q 追加段用了两个不同的时间戳）；URL 编码级别（一次 vs 二次编码）在 5 个系列实验里反复搞错。同一批实验反复得出"链模型成立/不成立"、"TLS 是/不是门槛"的震荡结论。

**AI 的辩护**："变量太多是因为想加快排查速度，一次测完所有可能性。"

**为什么不成立**：
- 多变量同时改变时，失败无法归因——S11 失败后只能再拆 4 个实验，比单变量逐个排除更慢
- 实验代码 bug（编码级别、参数不同源）制造的假阴性比不做实验更糟：它会"证伪"本来正确的假设
- 震荡的根因是每轮实验结论都建立在未验证的实验代码正确性上

**正确做法**：
1. **一次只改一个变量**，其余全部复用最近一次成功请求的配置（阳性对照连续性）
2. **实验代码先自检再发请求**（无网络成本的本地检查）：URL 编码级别与浏览器成功样本逐字符 diff、签名内 t 与 q 末段 t 同源、时间戳新鲜度、cookie 完整性——四项检查过一遍再发
3. **每组实验带阳性对照**：同一会话内先复刻一次已知成功的请求确认通道/状态正常，再发测试请求；阳性对照失败 ⇒ 本组实验作废
4. 结论落盘用"实验矩阵"格式（请求构造 × 结果），禁止靠事后回忆复述实验结论

**判定测试**：翻实验记录——是否存在"单轮改动 ≥2 个变量仍下结论"、"无阳性对照"或"实验代码未与成功样本做过逐字符对比"的记录？有即违反本条。

## 反模式 15：对照实验失败后归因"服务端深度校验加密指纹"而不自查实验代码 → 误判魔改

**实战案例**：猿人学第6题（match6，RSA 签名）

**AI 的操作**：还原出 m = RSA-1024 PKCS#1v1.5(base64("1|"+t)) 后做对照实验：同一会话、同一链、同一 cookie 下，浏览器 JSEncrypt 生成的 m 成功、Python 标准库生成的 m 失败。据此宣布"站点魔改了 jsbn SecureRandom（确定性 RC4），服务端校验解密后 PS 字节序列，标准库随机密文被判死"，并沿该结论继续深挖 PRNG 复刻。最终二分实验（page/链长交叉验证）证明：**任何合法 PKCS#1 填充的密文服务端都接受**——Python 密文被拒的真因是 Python 侧 URL 编码/实现细节 bug，与"魔改 PRNG 被校验"无关（该站确实魔改了 PRNG 种子为确定性 RC4，但服务端无法也无意校验它）。

**AI 的辩护**："对照实验控制了所有变量，唯一差异就是密文来源，结论是铁证。"

**为什么不成立**：
- 对照实验的"唯一差异"依赖实验代码自身正确——Python 侧构造 URL 时编码层级/明文细节有 bug，"唯一差异"实际是"密文来源 + 编码 bug"两个变量
- 阳性对照（浏览器 m）成功只证明通道/会话正常，**不能反证测试组失败归因于密文本身**
- "服务端校验 PS 序列"在密码学上需要服务端能预测客户端 PRNG 种子——下这类结论前应先做可行性 sanity check

**正确做法**：
1. **对照实验失败先自查实验代码**：测试组请求构造与最近一次成功样本逐字符 diff（URL 编码层级、明文构造、参数同源、时间戳格式），排除实现 bug 后才考虑归因服务端
2. **确定性加密判定法（排查工具，非降级依据）**：对同一明文调用两次加密函数，密文相同 ⇒ 加密是确定性的（PRNG 被魔改）。但注意：**确定性 PRNG 存在 ≠ 服务端校验 PS**——确定性只说明客户端随机源被魔改，是否影响服务端接受度需另行验证
3. 随机源被魔改且需与浏览器逐字节一致时：优先在 vm/沙箱内直接运行原始加密闭包（同份代码同一份随机流），而非纯算复刻 PRNG

**判定测试**：宣布"服务端校验密文内部结构（PS/IV/随机段）"前，是否已排除实验代码自身的编码/实现差异（与成功样本逐字符 diff 过）？没做过 diff 即下结论，或把"确定性 PRNG 存在"直接等同于"服务端校验 PS"，即违反本条。

## 反模式 16：取证被阻断后跳过 Step 2 硬扛补环境 → 打转数十轮不诊断不止损

**实战案例**：猿人学第5题（match5，2026-08 中途会话）

**AI 的操作**：

3. 触发 20+ 步止损线：落阶段报告 + 向用户输出卡点与方向选项；「问 vs 不问」摇摆超过 2 轮即视为已触发，必须执行 SKILL.md 4.4 检查点动作序列
4. 取证探针：优先标准脚本参数（`--ua` / `--cookie` / `--click`）；确需手写时方法名先内省（`dir(page)`），禁止按 Playwright API 命名习惯猜

**判定测试**：翻执行记录——死循环/打转期间是否做过至少一次根因诊断（Proxy 探测 / timeout 定位 / 缺失属性清单）？跳过 Step 2 进补环境前是否有用户确认或检测证据支撑的显式降级声明？「问用户 vs 再试一轮」摇摆是否超过 2 轮？用「插桩 while(1)」定位空转即违反本条。任一为是即违反本条。

## 反模式 17：方案已定却反复重新权衡——纯思考打转，零工具调用产出

**实战案例**：猿人学第7题（match7，动态字体反爬）

**AI 的操作**：还原方案已全部确定（字形指纹字典 + requests 直连 + 末页 UA=yuanrenxue）后，在「是否现在写 final.py」「用 requests 还是 curl_cffi」「指纹字典来源是否合规」上反复自我确认约 300 行思考、20+ 轮"Write final.py now / Go / finish / proceed"，期间没有任何工具调用；同一会话早期还反复重新判断「match/7 未收录」这一已有结论（4 次以上），并在「提交答案要不要先问用户」（B 档规则本就是宣布+继续）上摇摆不定。

**AI 的辩护**："再确认一次方案更稳妥，避免写错返工。"

**为什么不成立**：
- 重复权衡不产生新证据——方案正确性只能由执行后的验证结果判定，思考内的第 N 次再确认与第 1 次的信息量完全相同
- 打转消耗的是上下文预算：300 行思考换 0 个工具调用，等于把本可用于验证与修复的轮次提前烧掉
- 决策循环常伪装成"严谨"：每轮都像在推进（措辞不同），但决策集合没有任何变化

**正确做法**：

3. 连续两段思考之间没有工具调用 = 正在打转，立即停止思考转执行
4. 对"是否合规"类疑虑：查一次规则原文，规则允许即执行，规则禁止即停——不存在"查多次更合规"

**判定测试**：翻思考记录——同一决策句（如「现在写 final.py」）出现 ≥3 次仍无对应工具调用，或同一索引/结论被重新查询 ≥2 次，即违反本条。

## 反模式 18：同站经验跨题无差别迁移（开窗/蜜月期照搬）→ 登录态被重置

**实战案例**：猿人学第7题（match7）

**AI 的操作**：从 match5/6 案例把「先 GET HTML 开窗（蜜月期）再请求数据」整步迁移到 match7：开窗后请求 5 页数据、再提交答案。结果开窗的 HTML 响应 `Set-Cookie` 下发了新的匿名 sessionid，**覆盖**了注入的登录 sessionid，提交答案持续返回 401 not login；排查数十轮（怀疑 cookie 域匹配、csrftoken、账号封禁）才定位到开窗是根因——而 match7 数据接口根本不需要开窗。

**AI 的辩护**："match-index 写明第 4/5/6 题风控底座同源，新题直接按此基线排查。"

**为什么不成立**：
- 同站不同题的接口风控配置相互独立：match5/6 的蜜月期校验在数据接口上，match7 的数据接口带 sessionid 直接请求即 200——开窗是纯多余请求
- 开窗请求本身有副作用：HTML 响应可能下发新会话 cookie 覆盖注入的登录态，越"预热"越坏
- 速查表的"基线排查"是**假设清单**（按序验证哪些特征本题也存在），不是**步骤清单**（逐项照搬执行）

**正确做法**：
1. 同站经验迁移前先小成本验证：直接带登录 cookie 请求一次数据接口，200 即本题无需开窗，跳过该步骤
2. 确需开窗的 case：开窗后、任何写请求前复查 cookie jar 中登录 cookie 是否仍为注入值，被覆盖则重设
3. 401 not login 且数据接口同时正常时，优先怀疑「会话 cookie 被中途覆盖/重置」（开窗、HTML 预热、重定向），再查账号状态

**判定测试**：翻执行记录——引用上一题流程步骤（开窗/预热/间隔 sleep）前，是否有本题接口的直接验证记录？开窗后是否复查过登录 cookie？没有即违反本条。

## 反模式 19：数据差异未先排除会话因素 → 误判"平台行为/风控"

**实战案例**：猿人学第9题（match9）

**AI 的操作**：拉取数据时发现每次请求数据不同、与预期不符，怀疑"平台数据按周期重置"或"IP 被限流"，转向调整频率/换代理/重跑；实际机制是**数据绑定会话**——匿名会话每次请求数据不同、固定会话凭证数据恒定。

**AI 的辩护**："数据一直变，肯定是平台定时重置或风控。"

**为什么不成立**：
- 数据接口的数据可能绑定会话而非全局：匿名会话每次不同 ≠ 平台重置，固定会话凭证重放即可验证
- 会话 cookie 可能由 API 响应 set-cookie 下发（非页面），"换会话"的时机完全不可见
- 归因到"周期重置/IP 限流"会引导到换 IP/降频等错误方向，浪费预算

**正确做法**：
1. 数据差异先做会话绑定验证：固定会话凭证（cookie/Authorization 等）重放同一请求两次，数据恒定 → 绑定会话，后续请求固定复用该会话
2. 确需"换会话"时，确认会话凭证来源（页面 set-cookie / API set-cookie / JS 生成），替换后重放验证数据是否变化
3. 先排除签名/会话因素，再归因平台行为（重置/限流/缓存轮换等）

**判定测试**：翻执行记录——把"数据变化"归因到平台行为/风控前，是否先做了固定会话凭证重放实验？没有即违反本条。

## 反模式 20：VM 沙箱补环境卡死后转投浏览器黑盒取数

- 实际根因不是"环境检测太难"，而是 AI 跳过 IMPLEMENT 准入三件套（未产 entry-chain.md/missing-env-priority.md、未过 check_env_prerequisites.js）直接写 vm 执行框架，盲补环境必然空转

**正确做法**：

3. 定位到内核级检测（eval.toString/Error.stack 等，UA 覆盖无效）：按状态机 `BLOCKED_FORENSIC` 对齐用户（用户材料 / 确认降级），把路线选择权交还用户
4. 不得转投浏览器内核取数方案：即使中途用浏览器验证思路，交付物必须是纯协议实现；浏览器脚本不得进 result/，挪到 case/ 也算交付违规

**判定测试**：翻执行记录——vm 补环境卡死后是否做过根因诊断（Proxy 探测 / timeout / 缺失属性清单）？是否过 IMPLEMENT 准入三件套？交付物 final.js/final.py 是否纯协议（无 ruyipage/playwright/puppeteer 依赖）？任一为否即违反本条。

> 后记：match10 已于 2026-08-26 完成纯协议修正（vm 沙箱黑盒 rs.js/boot/core 全链 + Node 原生 https，5/5 页通关，见 `cases/yuanrenxue-match10-ruishu3-replay-defense.md` 终局版本）。违规过程教训保留——同一案例从"卡死转投浏览器"到"纯协议通关"只差：准入三件套 + 配套资源纪律 + 元素语义补齐。

## 反模式 21：外部失败未验证签名内容就归因「TLS 指纹/会话强绑定」

**实战案例**：猿人学第10题（match10，瑞数 v3 变种，2026-08-25 浏览器方案期误判）

**AI 的操作**：浏览器内请求 200、外部客户端（Node https / curl_cffi 全量复刻 header+cookie+TLS 指纹）400 → 据此宣布「m 与浏览器会话强绑定，外部精确复刻必失败」「TLS 指纹检测封死纯协议」，把浏览器黑盒取数当作交付，并将「TLS 封死」结论写进案例库收录为反例。

**AI 的辩护**："连接层所有可复刻项都复刻了仍 400，唯一差异只剩浏览器环境本身，说明拦截在通道层。"

**为什么不成立**：
- "外部精确复刻"复刻的只是**请求表象**；签名内部内容未经中间值验证——本例 m 动态段全零（boot+api2 不配套导致），签名内容本身就是错的，请求格式再完美也是 400
- 签名零值填充是**肉眼可辨的退化信号**（本例 m 动态段输出字母表 q 重复填充串），它指向补环境不完整，不需要任何通道层实验即可发现——没人去看签名内容本身
- 终局验证：Node **原生 https 直连**（无任何 TLS 指纹伪装）全通，证明该站根本没校验 TLS 指纹，"TLS 封死"是彻头彻尾的误判
- 误判有双重代价：既诱导中途交付违规方案（反模式 20），错误结论还会进入案例库误导后续同站案例（本例已被终局修正）

**正确做法**：
1. 外部请求失败先 dump 签名内部中间值，与浏览器样本逐段对比（对齐探针法，`references/env/env-detect-bypass.md`），确认签名**生成内容**正确
2. 检查签名输出的退化特征：零值填充段（如 qqq 重复）、恒定段、与浏览器样本的段级 diff——这些是签名输入错误（环境缺失/资源不配套）的直接证据
3. 签名内容确认正确后才考虑通道层归因，且通道层结论需分层正反对照实验支撑（反模式 11 的判定测试）
4. 「TLS 封死」「会话强绑定」类通道层结论写入案例库/经验沉淀前，必须已有纯协议通关记录或分层对照实验证实，禁止仅凭"复刻了还失败"推断

**判定测试**：宣布「TLS/会话强绑定拦截」前，是否存在签名内部中间值与浏览器样本的对比记录？签名输出的零值/填充段是否已被解释并归零？没有即违反本条。
